# cultcodex.me — Full audit 2026-09-30

Scope: the live site (https://cultcodex.me, Fly app `cultcodex-v2`, v55) plus the
`master` codebase. Follow-up to `AUDIT-2026-09-24.md`. Nothing was changed; this
file is the only write.

## Verdict

Healthy and well-hardened on security, **fragile on availability and speed**.
The 09-24 security fixes hold, and the cold-start DB timeouts in the post-deploy
report are the visible edge of a bigger issue: every episode page is rendered
live against a 5-connection database pool on one small machine with no CDN.

## Findings

### Critical / High

**C1. Episode pages are fully dynamic and fail into a 404.** *(High)*
`src/app/episodes/[slug]/page.tsx:59` sets `dynamic = "force-dynamic"`. Each view
runs roughly 10 queries (`getEpisodeBySlug` with a large include, related, favorites,
reactions, comments, neighbors, entities). The response is
`cache-control: private, no-store`, so nothing is ever cached. Line 96 does
`getEpisodeBySlug(slug).catch(() => null)` then `notFound()`, so **a DB timeout on
a real episode is served as a 404**. Observed live today: `/episodes/rumor-rodeo`
(a sitemap URL) returned Next's error shell with `noindex`, then a 404, then 200;
the same URL timed 2.8s, 20s, 13s, then 0.7s. A crawler hitting this during a
slow moment can drop or de-index the page.
*Fix:* (a) distinguish "not found" from "query failed": only `notFound()` on a
null result, and let real errors throw so they return 500/503 (retryable) instead
of a cacheable 404. (b) Make the page ISR: drop `force-dynamic`, use
`revalidate = 3600`, and move the per-user bits (favorite state, reactions for
the viewer, subscription gating) into a small client island or a separate
dynamic request. `generateStaticParams` already exists (line 61).

**C2. Single small machine, pool of 5, no CDN.** *(High)*
`fly.toml`: 1 x `shared-cpu-1x` 2GB. `src/lib/db.ts`: pool `max: 5`,
`connectionTimeoutMillis: 5000`, `idleTimeoutMillis: 10000`. DNS resolves straight
to Fly (66.241.125.104, no `cf-ray`), so the `s-maxage` headers do nothing and
`public/` (607MB, 588MB of it `public/cards`) plus every JS/CSS file is served from that one machine.
Any crawler burst or traffic spike queues on 5 connections and then times out,
which matches the post-deploy `timeout exceeded when trying to connect` burst.
*Fix, in order of payoff:*
1. Put Cloudflare (proxied) in front; the docs already plan it. Cache `/_next/static`, images and ISR HTML.
2. Move `public/cards` to R2 (`src/lib/r2.ts` already exists). This also shrinks the image and deploy context.
3. Raise `idleTimeoutMillis` to 30-60s (10s makes the pool reconnect, with a full TLS `verify-full` handshake, between bursts), and raise `max` toward 10 if the Xata plan allows it.
4. Run 2 machines (`fly scale count 2`) for redundancy and zero-downtime deploys. This needs C4 first.

**C3. Cold cache after every deploy.** *(Medium-High)*
The Next cache lives on the container disk, so each deploy starts empty. First
hits measured today: `/psychenomicon` 10s, `/episodes` 5.5s, `/people` 1.7s.
Repeat hits: 0.2-0.4s.
*Fix:* after the deploy health check in `.github/workflows/deploy.yml`, add a warm-up
step that curls the top ~30 URLs (home, `/episodes`, `/people`, `/topics`,
`/lore`, `/psychenomicon`, `/stats`, recent episodes). Combine with C1 (ISR) and a
CDN and the post-deploy timeout burst goes away.

**C4. SSE connections count against the concurrency cap.** *(Medium-High)*
`api/sse/live/chat` and `api/sse/episodes/[slug]` hold a request open per viewer.
`fly.toml` sets `hard_limit = 100` requests, so roughly 100 open streams block
every other request on the machine. `src/lib/sse/event-bus.ts` is in-process, so it
also silently breaks with a second machine (a chat message posted on machine A
never reaches viewers on B).
*Fix:* cap connections per IP and overall (return 429 past a limit), raise
`hard_limit` if the stream count is expected to be large, and before scaling
past one machine move the bus to Postgres `LISTEN/NOTIFY` or Redis.

### Medium

**M1. Failing test is environment-dependent.** `src/lib/providers/gemini.test.ts`
("reports an absent key as unconfigured") fails whenever `GEMINI_API_KEY` exists
in the environment, because `new GeminiProvider("")` falls back to `process.env`.
Fix: `vi.stubEnv("GEMINI_API_KEY", "")` in that test.

**M2. Transitive vulnerabilities.** Run `npm audit fix` and commit the lockfile.
brace-expansion is high severity (quadratic expansion, CPU denial of service) but
only reachable through build tooling, so the practical risk is low.

**M3. Oversized pages.** Uncompressed sizes: `/timeline` 2.7MB, `/graph` 1.0MB,
`/people` 479KB, `/cards` 362KB. Gzip helps, but the HTML and RSC payload is
still large. Paginate or lazy-load `/timeline` by era, and load `/graph` data
from a separate JSON endpoint cached at the CDN.

**M4. `force-dynamic` on 150 routes.** Many are archive templates (people,
topics, lore, series). Each one is a DB query per view. Convert read-mostly
ones to `revalidate` (300-3600s), keeping `force-dynamic` only for per-user pages.
This is the same root cause as C1, so audit them together.

**M5. Rate limits are per-process.** `src/lib/rate-limit.ts` resets on every
deploy and does not share across machines. Cost-bearing routes already pair it
with the DB-backed `sharedRateLimit`, so the gap is the cheap routes: `tarot/reading`,
`cards/packs`, `episodes/random`, `search/suggest`-adjacent, and the SSE routes.

**M6. GET endpoints that change state.** `subscribe/unsubscribe` (GET) deletes
the subscriber. Mail-security scanners prefetch links, so a person can be
unsubscribed without clicking. Token-gated, and a POST one-click path exists, so
make GET show a confirm page and do the delete on POST. (Still open from 09-23: N5,
admin GET routes that write, and non-expiring admin HMAC keys.)

### Low

- **L1.** CSP allows `script-src 'unsafe-inline'`. Moving to nonces is a larger
  change with Next 16 but is the main remaining hardening step.
- **L2.** Stale Vercel wording remains in `src/lib/db.ts`, `nav.ts`,
  `keep-alive/route.ts`, `stripe/checkout/route.ts`, `errors/route.ts` and some
  scripts (N10). Also `scripts/enrich/run-via-vercel.ts` is dead now.
- **L3.** Not-found responses are 62KB because they render the full site
  chrome. Fine for users, wasteful for crawler probes.
- **L4.** `/api/stats`, `/api/episodes`, `/api/search` return 404, so there is no
  public read API. See the feature list if that is wanted.
- **L5.** Test coverage: 93 test files for ~960 source files. No route-level
  tests for the pages that matter most (episode, search, oracle).
- **L6.** Homepage has 7 icon-only buttons without an `aria-label`. Add labels.
- **L7.** Open from 09-24: R4 (no baseline migration, a fresh DB cannot be
  built from `prisma migrate deploy`).

## What is solid

Security headers and HSTS preload, admin gating in two layers, Stripe webhook
with signature check plus event idempotency table, HMAC-signed subscriber links
with timing-safe compares, secrets kept in env rather than code, SHA-pinned
GitHub Actions, TLS `verify-full` to the database, AI-crawler policy, structured
data (Organization, WebSite, SearchAction, Person, BreadcrumbList), canonical
URLs, alt text on every image checked, working sitemaps, feed.xml and llms.txt.

## Structured data gap

Episode pages should carry `VideoObject` / `PodcastEpisode` JSON-LD (name,
description, uploadDate, thumbnail, duration, embedUrl). The people page has
`Person` and `BreadcrumbList`, but the home, `/episodes` and `/search` pages
only have the site-wide types, and the episode page could not be checked because
of C1. Add `VideoObject` plus `BreadcrumbList` there; it is the biggest SEO upgrade
available for a 3,300-episode archive.

## Upgrade and feature ideas

- **Public read API** (`/api/v1/episodes`, `/people`, `/search`) with API keys, as
  a paid tier for researchers and bot builders; the queries layer already exists.
- **Saved searches and alerts:** email or push when a new episode matches a
  topic, guest or phrase. Web-push and Resend are already wired.
- **Transcript deep links and clip sharing:** timestamped permalinks plus an
  auto-generated quote card (the OG image pipeline exists) for social sharing.
- **Episode-page "what's new" digest:** weekly email of new episodes, new lore
  entries and top quotes, from the `gift-sequence` and `ingest-latest` jobs.
- **Semantic search on the homepage:** surface the pgvector search that exists
  today behind `/search`, with example concept queries.
- **Uptime and synthetic checks:** a scheduled job that loads 20 random sitemap
  URLs and alerts on any 404/5xx or p95 over 3s. This would have caught C1 before a crawler did.
- **Observability:** Sentry is installed; add a DB pool gauge (waiting clients)
  logged each minute so pool exhaustion shows up before users feel it.
